## 〇之二、跨机可复现（task-14，kernel-astro 自域缺陷）

出生时刻 `birth` 是**无时区数字**，原实现用 `new Date(y,m-1,d,h,mi)` 构造 → 按宿主时区（含历史 DST）解释，同一份出生资料在不同机器上得到不同天象。

| 宿主 TZ | 解释出的 UTC 瞬时 | birthChart.astro.sunLon |
|---|---|---|
| `Etc/GMT-8`（本机默认） | 1990-05-12T01:30Z | 51.07922（＝契约 §6 oracle 的 51.08） |
| `Asia/Shanghai` | 1990-05-12T**00:30**Z | 51.03899 ← 同名义 +8，却因**中国 1990 年夏令时**差 1 小时 |
| `UTC` | 09:30Z | 51.40103 |
| `America/New_York` | 13:30Z | 51.56192 |

**修法**：固定 `UTC+8` 偏移（`Date.UTC(y,m-1,d,h,mi) − 8h`），**不查时区库**（否则历史 DST 会再次引入不可复现性）；`renyuan` 的"自节令起日数"也改为两端同口径的**民用时刻差**。
**复验**：五时区（`Etc/GMT-8`/`Asia/Shanghai`/`UTC`/`America/New_York`/`Europe/London`）下 `birthChart.astro.sunLon` **逐位相同 = 51.07922**；出生盘四柱/农历/renyuan 同样逐位相同。
**`when` 语义未动**：仍是绝对瞬间，跨时区本就代表不同瞬间，故 `chart.astro` 随 TZ 变化是**正确**的（任务书第 2 条要求不动它）。
**口径落点**：`calendar.js` 文件头「时间口径」表、`birthChart.tz`（含推导出的 UTC 瞬时）、`meta.timeConvention`。

> ⚠ **契约 §6 的 oracle 前提**：`docs/V2-CONTRACT.md §6` 所载「太阳 51.08°、木星 98.90°、土星 295.30°」三个值，**以 UTC+8 固定偏移（即本机 `Etc/GMT-8`）为前提**；在 `TZ=UTC` / `America/New_York` 下用同一份**民用时刻**输入会得到不同值——这不是实现错，是输入的时区语义变了。本报告由 verifier #2 独立复现该前提，记此存档。
> 另：`#105 西洋占星` 未报纬度时返回「RAMC+90」（东点赤经），与标准上升式在 φ=0 的值差 **0.690°**（后者才是上升点）——已独立复算确认，详见 `v1-crosscheck.md` 轮次台账 R3-5。
